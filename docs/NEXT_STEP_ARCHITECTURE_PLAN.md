# 下一階段：架構評估與第一個可玩版本

> 狀態：建議方案，尚待確認；目前沒有修改遊戲 HTML，也沒有建立新遊戲原型。

## 建議結論
採用「模組化原始碼 + 可部署單一 HTML 成品」的方向評估。保留既有 HTML 當作歷史版本與行為參考，新原型使用獨立目錄，不直接覆寫舊檔。若實測發現模組化增加手機瀏覽器或部署風險，再調整打包方式，而不是先把所有邏輯重新塞回單一巨大檔案。

## 為什麼
- 遊戲預期會擴充境界、功法、物品、事件、地圖與角色互動，資料與邏輯需要分開管理。
- 原著資料可獨立核對與修訂，不必每次改一段設定都動到戰鬥或存檔邏輯。
- 既有 HTML 保留，可隨時比較舊行為並降低重寫風險。
- GitHub Pages 可以部署靜態成品；建置產物可視需求輸出單一 HTML，以降低部署依賴。
- 這是建議而非已確認決策，需先做小型技術驗證。

## 建議目錄草案
- `src/core/`：遊戲狀態、時間、規則與事件派發
- `src/systems/cultivation/`：修煉、突破、離線收益
- `src/systems/exploration/`：地點、探索行動、遭遇
- `src/systems/combat/`：戰鬥規則
- `src/data/realms/`：境界資料與原著考證狀態
- `src/data/items/`：物品、丹藥、材料、法器
- `src/data/events/`：事件條件、選項與結果
- `src/ui/`：手機介面與導覽
- `src/save/`：存檔驗證、版本遷移、備份與復原
- `tests/`：規則與存檔測試
- `dist/`：部署成品（由建置流程產生）
- `legacy/` 或既有根目錄檔案：保留舊 HTML，不在新原型穩定前移除

目錄名稱是提案，可依實際技術選擇調整。

## 第一個可玩版本（垂直切片）建議範圍
必須有：
1. 建立角色與顯示基本狀態。
2. 自動修煉、前景時間計算、離線收益。
3. 修為達標提醒，玩家手動選擇突破。
4. 至少一條可驗證的突破規則，不以固定通用成功率取代尚未考證的原著規則。
5. 存檔、讀檔、資料版本欄位與基本錯誤處理。
6. 一個探索地點、一項資源、一個有條件觸發的文字事件。
7. 手機窄螢幕可操作，並測試重新整理、關閉再開、離線返回及重複計算。

暫不納入：
- 完整仙界內容、龐大原著事件庫、完整宗門／秘境、完整交易製作、複雜戰鬥與多結局主線。
- 未完成原著考證的高境界細節。
- 雲端同步與帳號系統。

## 存檔策略
- 新原型採用新的版本化 schema；先不要直接沿用 `mortalCultivationSaveV2` 以免與舊版互相覆寫。
- 初期可先支援新原型自身的存檔與重置。
- 是否匯入舊版存檔，需先比較資料欄位與語意；不應假設直接相容。
- 每次載入先驗證資料形狀；遇到無效資料時保留原資料並提供復原／重置選項。
- 離線收益需記錄時間戳並防止負時間、重複結算及過長間隔。

## 開始寫新原型前的驗收條件
- 目錄與建置方式決定。
- 角色／修煉／資源／事件／存檔資料模型有簡短規格。
- 離線收益、突破與存檔至少有可重複執行的測試案例。
- 手機瀏覽器實測方案清楚。
- 舊 HTML 保留且不被新原型存檔覆寫。
